# iOS readiness

What must change or be built to produce a working iOS build of the app. Written 2026-10-25 by the user's order. This is
an exception to the "no other docs" rule; it is a plan, not a description of the code. Nothing here is started; the
work is on hold (TODO.md, On hold, item 137 iOS build).

Paths are relative to the repository root. `KT` means
`apps/app/modules/health-connect/android/src/main/java/expo/modules/healthconnect`.

Sizes: **S** under a day, **M** one to three days, **L** more than three days or several tasks. Risk is the chance the
iOS result cannot match Android. **Blocker** means nothing after it can work without it.

---

## Summary

- The JavaScript app is close to iOS-ready. Every native module is loaded with `requireOptionalNativeModule`
  (`apps/app/modules/health-connect/src/*.ts`, `apps/app/src/platform/*.ts`), so an iOS build with no native code of our
  own compiles and starts. All Expo SDK 57 packages and the third-party packages in `apps/app/package.json` support iOS.
- The native side is Android-only and very large: one local module (`apps/app/modules/health-connect`,
  `expo-module.config.json` has `"platforms": ["android"]`) with 10 Expo modules, 369 Kotlin files, about 36,000 lines
  (plus 119 test files), covering hub networking, Health Connect, Bluetooth devices, the watch, calls, talk, wake
  listening, the overlay, the phone node and push commands. None of it exists for iOS. About half has an iOS
  equivalent, and the rest cannot exist on iOS at all.
- The app thinks every native platform is Android: `appPlatform()` returns `'android'` whenever `Platform.OS !== 'web'`
  (`apps/app/src/design/platform.ts`). An iPhone would mount Android-only hosts, settings and push code. This must be
  fixed first.
- The hub and the shared contract only know Android phones: `CLIENT_PLATFORMS`, `PAIRED_PLATFORMS` and `PUSH_PLATFORMS`
  (`packages/domain/src/api/primitives.ts`, `endpoints-access.ts`, `rows-media.ts`), SQLite CHECK constraints
  (`apps/hub/src/store/migrations/core-tables.ts` clients, `more-tables.ts` push_targets), push is FCM only
  (`apps/hub/src/extensions/push/fcm.ts`), and ringing and phone identity filter on `'android'`
  (`apps/hub/src/reach/ring-transports.ts`, `apps/hub/src/phones/phone-identity.ts`).
- There is no Mac. Expo's cloud build (EAS Build) builds, signs and distributes iOS apps from Linux. Metro keeps running on
  the laptop and an iOS dev client loads from it over the LAN like the phone does now. Writing and debugging about
  20,000 lines of new Swift without a Mac is slow (each native change is a cloud build of 15 to 30 minutes, and there is
  no simulator), so a Mac, rented or bought, is recommended before the native phases.
- Apple Developer Program membership ($99 a year) is required for any install on a real iPhone longer than 7 days, for
  push, HealthKit and every entitlement below.
- Fastest useful result: phases 1 and 2 below (config, build pipeline, platform model, hub enums) give an iPhone app
  that connects through the public URL and shows everything that needs no native code (devices, cameras, automations,
  assistant chat, maps, settings). Health, Bluetooth, calls, talk, wake and the phone node follow as separate native
  phases.
- No real iPhone or iPad model is known. Per the global rules, the exact device must be named before any native work
  is planned in detail.

**Build host options and costs** (prices as known in 2026; check before buying)

- EAS Build (Expo cloud): free plan has a small monthly number of low-priority iOS builds; paid plans start at about
  $19 a month with build credit, then roughly $1 to $4 per iOS build. No Mac needed. Best for phases 1, 2 and release
  builds.
- GitHub Actions macOS runners: free for public repositories; for this private repository macOS minutes cost about
  $0.06 to $0.08 each, so a 25-minute build is about $2.
- Codemagic: free personal tier with about 500 macOS minutes a month.
- Rented Mac: MacinCloud about $25 to $60 a month; Scaleway Mac mini about €0.10 to €0.25 an hour with a 24-hour
  minimum; AWS EC2 Mac dedicated host about $15 to $25 a day with a 24-hour minimum. Gives Xcode, a simulator and
  remote desktop.
- Buying a used Mac mini (Apple silicon, 16 GB) about $350 to $600 once. Gives local Xcode, simulator, Instruments and
  fast native iterations. Best value if the native phases are done.

## App Store and review rules that affect us

- Only App Store and external TestFlight builds are reviewed. Ad hoc builds and internal TestFlight builds are not, but
  every App Store Connect upload is checked automatically (missing usage strings, private API use, privacy manifest).
- HealthKit (guideline 5.1.3): only for health features, a privacy policy, no advertising use, no health data in iCloud.
  Sending it to the user's own hub with consent is allowed.
- Always-on microphone (2.5.4 and 5.1.1): background audio must serve a visible feature; a wake-word app is often
  questioned. High risk for the App Store, no issue for ad hoc.
- Local network: allowed with a clear usage string.
- VoIP pushes must always show a CallKit call, or the app loses VoIP push delivery.
- Private APIs (volume slider tricks, lock, screenshots) are rejected and can fail an upload; do not use them.
- Review needs a working demo (2.1): a self-hosted hub app needs a demo hub and account for reviewers.

## Decisions needed

Each has a recommendation; the coordinator decides.

- **D1 Distribution.** Ad hoc, TestFlight internal or App Store. Recommendation: ad hoc for the dev client and
  TestFlight internal for release builds; no App Store (review risk from the always-on microphone and the self-hosted
  hub).
- **D2 Build host.** EAS only, GitHub Actions macOS, rented Mac or a bought Mac mini. Recommendation: EAS Build for
  phases 1 and 2; a used Apple silicon Mac mini (or a monthly rented Mac) before phase 3, because the Swift port is large
  and needs Xcode, a simulator and fast iterations.
- **D3 Target device.** No iPhone is known. Recommendation: the user names the exact iPhone and iPad models and iOS
  versions before phase 1 task 7; nothing native is planned in detail before that.
- **D4 Bundle id.** Recommendation: the same id as Android, `com.devl0rd.smarteverything.dev`, so the hub sees one app.
- **D5 Native strategy.** Port Kotlin one to one into Swift, or move pure protocol logic into shared TypeScript.
  Recommendation: transports, background and OS integrations in Swift; pure parsers and rules moved into
  `packages/ble` and `packages/domain` where the JavaScript is running anyway; background-critical paths (Bluetooth
  restoration, HealthKit background delivery) stay native.
- **D6 Push transport.** APNs directly from the hub, or Firebase for iOS too. Recommendation: APNs directly, because
  VoIP, push-to-talk and Live Activity pushes need APNs anyway and it avoids the Firebase iOS SDK.
- **D7 Features dropped on iOS.** Overlay windows, accessibility control, notification listener, app usage, settings
  writes (volume, ringer, DND, brightness, timeout, toggles), screenshot and lock, other apps' media keys, default
  assistant, watch notification forwarding and call relay, boot restarts. Recommendation: drop them and show each as
  unsupported on iPhone with its reason, using the existing feature states.
- **D8 Overlay alternative.** Recommendation: a Live Activity with Dynamic Island, as an optional later phase.
- **D9 Wake listening on iOS.** Recommendation: build it as opt-in, started in the foreground and kept alive with the
  audio background mode; accept that it stops after a reboot or kill and say so in the app; only with D1 not the App
  Store.
- **D10 Watch on iOS.** Recommendation: a short spike with the real Watch S5 over BLE first; drop the watch on iOS if it
  does not connect, since the watch can only pair with one phone.
- **D11 iPad.** Recommendation: support it (`supportsTablet`), since tablet layouts exist.
- **D12 Minimum iOS version.** Recommendation: iOS 18 if the target device runs it (AccessorySetupKit, Control Center
  controls), never lower than the Expo SDK 57 minimum.
- **D13 First connection.** Recommendation: the public URL only for phases 1 and 2; the pinned LAN route arrives with
  the Swift `HubNetwork` in phase 3.
- **D14 Ring loudly.** Critical alerts need Apple's approval. Recommendation: use time-sensitive notifications with a
  custom sound; skip the critical alert request.
