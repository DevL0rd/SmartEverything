# Automation nodes

The node catalog is the contract: `automation_read` view catalog lists every kind with its ports, types and an example, and only those kinds and port names exist. Every port holds a literal or a wire; there are no formulas, so every calculation is its own node.

## Nodes and wires only

An automation is a flow chart of nodes joined by wires. Formulas, expressions and text templates do not exist anywhere: a port that needs a worked out value gets a wire from the output of a node that works it out. Build every program this way, step by step:

1. Every port, branch condition, case condition, structured output, variable start value and `admit` holds exactly one of two things: a constant `{"lit": value}` or a wire `{"wire": {"from": "<source>", "port": "<output>"}}`. Nothing else is accepted.
2. A wire's `from` is the `key` of a node that comes earlier (a loop or try gives `item`, `index` or `error` to the steps inside it), or one of five sources: `trigger` (the outputs of the trigger that fired, plus `key` and `at`), `inputs` (the inputs of a Custom Node or called automation), `vars` (a variable, by name), `home` (`timeZone`, `name`, `latitude`, `longitude`) and `run` (`id`, `startedAt`). `port` is one output name. To read a field inside a record, wire the record into Get field (`object.get`) and wire on from its `value`.
3. Work values out with calculation nodes. They never act, and can sit anywhere before the node that reads them: Compare (`logic.compare`: equal, not equal, greater, at least, less, at most), `logic.between`, Is one of (`logic.in`), And and Or (`logic.and`, `logic.or`: two to four flags wired into `a`, `b`, `c`, `d`), Not, Has a value (`logic.exists`), First available (`logic.coalesce`, with a `default`), Choose (`logic.select`: `condition`, then `whenTrue`, else `whenFalse`), Which trigger (`logic.trigger_is`), Add, Subtract, Multiply (two to four values in `a` to `d`), Divide, Remainder, Round, Clamp, Message (`text.format`: a fixed `template` whose `{a}` to `{d}` are filled from the values wired into `a` to `d`), Text check (`text.test`: contains, starts with, ends with, equals, is empty), Join, Count items (`list.length`), Get item (`list.get`: first, last or by index), Any item, Every item, Keep where and Find (`list.any`, `list.all`, `list.filter`, `list.find`: each compares every item, or one `field` of every record, by `test` with `value`), Field of each (`list.field`), Get field, Convert (`util.convert`: to number, text, on/off, duration, moment or list) and Lookup table (`util.lookup`).
4. Decide with wires too: an If branch `when`, a switch case `{"when": ...}`, the wait-for-condition `condition`, `admit` and the `condition` of `trigger.becomes_true` each take a wire to a flag, usually the `result` of a Compare, And, Or, Not or Has a value node. A switch on a value takes the wire in `subject` and fixed cases (`eq`, `in`, `range`).
5. An optional output (optional in the catalog) cannot feed a port that needs a value: test it with Has a value and branch, or pass it through First available with a `default`. A number wire fits any number port; for another type wire it through Convert.
6. Effects (device commands, notifications, tool calls, Value and variable changes) are always their own nodes on the run path, never inside a calculation.

Example: lights to step 1 when the step is 0 or no light is on. “stepIsZero” is a Compare with `a` a wire from `vars` port `step`, `op` eq and `b` 0; “noneOn” is a Compare with `a` a wire from “onNow” port `count` and `b` 0; `either` is an Or with `a` wired from “stepIsZero” port `result` and `b` from “noneOn” port `result`; the `flow.if` branch `when` is a wire from `either` port `result`.

Per-room logic is one Custom Node, never copies. Give it inputs for what differs per room (for example `lights` a target, `event` a choice, `sensors` a list of devices, `allowed` a flag), keep what it must remember in `persist` variables, and build its body from the nodes above. Each room's automation then holds its triggers and one `fn.call` with the room's constants and wires, for example `event` wired from a Lookup table or Choose fed by a wire from `trigger` port `key`. Change the Custom Node once and every room follows.

## Nodes

Common nodes: `device.set` (`target` device, devices, room or group; `control`; `to`; `percent`; `by` adds to a number), the temporary-set node of the `device` group (the control returns to its base after a time, when its `while` condition turns false, or when stopped; `priority` orders overlapping changes), `device.get`, `scene.run`, `flow.if`, `flow.switch`, `flow.repeat`, `flow.while`, the for-each loop, `flow.wait`, the wait-for-event and wait-for-condition nodes of the `flow` group, `notify.person` (really pushes), `notify.feed`, `notify.speak`, `var.get`, `var.set` and `var.change` (Values and variables), `automation.run`, `automation.stop` and `fn.call` (a Custom Node). A run keeps going when a scene or automation it uses is edited. Loops have no limit unless one is set: `flow.repeat`, `flow.while`, `flow.do_until` and the loop-until-break node `flow.forever` take an optional `limit` (`iterations`, `time` in ms, `onLimit` fail or end, optional `note`), the for-each loop runs any number of items at once with `concurrency`, and the automation's `budgets` (steps in a row, steps per run, loop passes, run chain length, side-by-side branches) are optional too; only `commandsPerMinute` (600) and the run state size guard (`runStateBytes`, 8 MiB) have defaults. A run never blocks the hub and `automation_stop` ends it at any time. A `flow.forever` needs a Break, Return or Stop inside or a `limit`; the checker names what a loop lacks.

`computer.audio` (`computer`, `change`) takes the `computer_audio_set` action and its fields, such as `app_volume` with `app` and `level`, `app_mute`, `app_output`, `volume`, `mute` or `default`. `computer.display` takes `change` `mode` (`output`, `width`, `height`, optional `refreshHz`), `scale`, `position`, `brightness` or `night_light`; HDR, rotation, main screen and turning screens off or mirroring them stay with a `tool.call` node. Read `computer_read` first for the exact names and the features the computer offers; a node the computer does not offer, a device that is not a computer, or (for a member) someone else's computer is refused when saved. Nobody is asked while it runs, so a screen change that can blank a screen (`mode`, `scale`, `position`) goes back by itself after 15 seconds unless someone keeps it at the computer. Add `keep: true` to keep it automatically once the hub has read the screen back and seen the change applied; if it does not match, the change is reverted at once and the node fails.

The run policy `mode` is single (default), restart, queue or parallel; queue needs `max` (and may take `maxWait`), parallel may take one. `key` names runs so `automation_stop` can end only those. Custom Nodes (`fn.call`) may call themselves or each other: recursion is allowed with no depth limit, and a runaway recursion is stopped by `automation_stop` or fails when its run state grows past `runStateBytes`. An `automation.run` node refuses to start an automation already in its own chain of runs unless it sets `allowSelf`.

`ai.wake` (`person`, optional `chat`, `instruction`) wakes that person's AI with what happened. `tool.call` (`person`, `tool`, `args`) calls any enabled tool without an AI turn, using the exact arguments from `tool_read`; for example `voice_speak` with `{"target":{"kind":"device","deviceId":"<camera id from presence_read>"},"text":"Exact words"}` says words once through a camera speaker. Both are for the owner; the editor offers them too, plus a ready "Say out loud" node for camera speakers, so anything you build the person can open and change. Old tool names still work.

Every automation records who made it in `author` (`via` person or assistant, and `profile_id`), and a plugin in `origin`; `author` is null only for automations made before this was recorded. Never create, change, switch, run or remove an automation the person did not ask for, and never touch one only because it looks wrong: say what you noticed.

## Integration nodes

Read the node catalog (`automation_read` view `catalog`) for exact ports. `ai.ask` runs one model call for a person and returns `text`, `result` (when a `shape` is given), `tokens` and `cost`; it has no tools unless `tools` names them, so give it tools only when none of its inputs come from outside the home. `ai.vision` does the same on pictures or a `camera` (the Bedroom camera stays blocked) and `ai.decide` returns a yes or no `answer` with a `reason`. A member's AI call runs as that member and stops at their budget. `camera.snapshot` stores a picture and returns its id for later `ai.vision` calls. `computer.power`, `phone.action`, `health.read` and `signal.emit` act on a computer, a phone, the person's health data or the signal bus; `http.respond` answers the webhook that started the run, once.

## More nodes

All of these are in the catalog; read it for exact ports. Pure ones only compute and never send anything.

- Devices: `device.snapshot` (Remember state) reads chosen controls of the target and `device.restore` puts them back, skipping offline devices and saying which. `scene.capture` saves the current values of devices as a scene (`overwrite` must be on to replace one of the same name). `device.fade` moves a number control (brightness by default) from one level to another over a time, paced by the command budget; stopping leaves it at the current level. `device.ensure` sends a value, waits for the device to report it and sends again if it does not, for devices whose cloud drops commands. `device.ir_send` presses a button of a learned infrared remote through its blaster.
- Readings: `computer.read` and `phone.read` return what a computer or phone reports now (a figure it does not report is left out), `signal.latest` reads the newest signal of one kind since the hub started (it never wakes a wait: use the wait-for-event node for that), `weather.forecast` reads the next hours (rain chance, wet hours, lowest and highest temperature, strongest wind) and `date.sun_times` gives sunrise, sunset, twilight, solar noon and golden hour (absent when the sun does not reach that day; fails when no home location is set).
- Flow: `flow.sequence` (Steps) only groups steps under a name for readability. `flow.forever` repeats until a Break, Return or Stop. `debug.breakpoint` (Pause here) pauses a dry run or simulation until the person continues.
- Logic: `logic.and`, `logic.or` and `logic.not` combine flags, `logic.changed` tells whether a value differs from the last run of this node in this automation (the first run counts as changed), `logic.count_true` counts true flags against `atLeast` and `atMost`, `logic.xor` is true when exactly one flag is, `logic.day_type` tells weekday, weekend or one of the dates you list (no holiday calendar is built in), `logic.in_schedule` tells whether a moment falls in weekly slots (a slot that ends after midnight belongs to the day it starts on).
- Numbers and chance: `math.convert_unit` converts within one kind of unit (temperature, length, power, energy, pressure, speed, colour temperature, volume), `math.percent` gives a percent of, a percent change or a percent value (a zero base fails), `random.chance` is true with a probability from 0 to 1 and `random.duration` picks a duration between a minimum and a maximum; random results are captured for the run and a simulation can seed them.
- Text: `text.case` trims, changes case or makes a slug, `text.slice` cuts, shortens with an ellipsis and pads, `text.speakable` writes a number, duration or moment the way it is said aloud (numbers and durations are English).
- Lists: `list.range` (numbers from one to another in steps), `list.slice` (a run, the first N or the last N), `list.sort` (numbers or texts, or records by a `field`; mixed kinds fail), `list.unique` (optionally by a `field`), `list.combine` (join, union, intersection or difference) and `list.reshape` (reverse, flatten one level, chunk or zip). To work through a list item by item use the for-each loop with `collect`, or `var.change` inside it to add up.
- Records: `object.fields` takes a record apart into keys, values and entries or builds one from entries, `object.merge` (a later record wins; `deep` merges inside records), `object.pick` keeps or omits listed fields and `object.remove` drops the field at a path (a missing path fails unless ignored).
- Time: `date.next` is the next moment a time of day comes round on chosen weekdays (daylight saving handled) and the start-of node of the `date` group is the first moment or last millisecond of a day, week (Monday), month or year in the home time zone.
- Secrets: `var.secret` hands a stored secret to a node that accepts one, such as the `auth` of `http.request`; its value is never shown, recorded or readable as text. Owner only.
