# Scenes, automations and schedules

## Choose the mechanism

- A scene is a flat list of device commands: `list_scenes`, `edit_scene`, `run_scene`.
- An automation is a program of connected nodes: triggers that start it, then logic, device, people and tool nodes. `list_automations` reads, `edit_automation` writes. A program with a `trigger.called` entry and no other trigger is started by `run_automation` or an `automation.run` node; declare its inputs there.
- A Custom Node is the same kind of program with an interface (inputs and outputs) that other programs place as a node, for example one per-room routine. It is read with `list_automations` view `functions` and written with `edit_automation` like an automation.
- A Value is a named on/off, number, duration or choice that nodes read and change: `list_values`, `edit_value`. A variable owned by one automation lives in its program, not in `list_values`.
- A one-off action for later is `list_scheduled` and `edit_schedule`. Update the matching item instead of creating a duplicate.

Read the home time zone with `get_home` for clock times. Keep the user's timing and target scope; ask only about ambiguity that changes what runs or when.

## Build from real contracts

Discover before writing: `list_automations` view `catalog` (filter `query`, `group` or `kind`) lists node kinds with their ports, types and examples, plus Custom Nodes. Use only kinds and port names it shows. Read `get_device` for every device control a node uses. Read `read_signals` with view `catalogue` and a `query` (a device, a room, a plugin or what you want to react to, optionally a `group`) to find the trigger: each row gives its source and kind, the ways to use it (`how`), its field and match keys and a plain-language sentence. View `kinds` lists every signal kind with its match values, then view `values` gives current examples. Never invent a signal kind, a match key or a trigger from a device name. A computer is a device: its readings (battery level, processor and graphics load and temperature, memory and disk use, network rates, locked, front app, display count on) and controls (volume, mute, audio output, microphone mute, brightness, night light, Do Not Disturb, power mode, playback, power actions) are capability keys in `get_device`. Per-app sound and per-screen changes have no key: they are the `computer.audio` and `computer.display` nodes.

A comparison against a missing value or a value of another kind fails the run: that means the home data is missing, so say so instead of working around it.

A match key with `values: null` has no fixed list and takes exact observed `data` or `details` values. Keep fixed lists for enumerated keys. Empty latest values do not prove a trigger unsupported. For camera sound events keep the discovered detection (Baby crying, Unusual sound, Loud sound are distinct; plain Sound is broad).

Computer app events: the events `app_opened` (an app gets its first window), `app_closed` (its last window goes), `app_focused` (it comes to the front) and `app_unfocused` (it leaves the front) carry the match keys `app` (name), `appId`, `title`, `user` and `personId`, and `list_events` reads them. To wait for an app to stay open or in front, trigger on the `computer` signals `app_open` or `app_focus` (value true or false, `field` the app id, `subject` the computer, match `app`) with test `{is: eq, to: true}` and `hold`, for example Firefox open for 30 minutes is `hold` 1800; each app is tracked on its own. They need the computer's `app_events` permission together with `apps` (on by default, owner only, listed in `get_computer` `permissions`) and are reported only by Linux computers with KDE or X11 window control.

Provider events with no named kind: nothing a device reports as an event is dropped. A Xiaomi event the home does not name, a SmartThings attribute that is not shown as a device value, a camera event-list type that is not a known detection and a read-only Tuya alert data point (alarm, alert, warning, fault, tamper, siren, trigger) that turned active all arrive as `activity` events. They carry a plain `summary`, and their own facts: `event` and `miotEvent` (Xiaomi name) with `arguments` (its values, not matchable), `attribute`, `capability`, `topic` and `component` (SmartThings), `code` and `value` (Tuya), `eventType` and `hasClip` (cameras). Read them with `list_events` and trigger on `source: event`, `kind: activity` with any of these as match keys. Camera detections also carry `source`, `eventType`, `hasClip`, `fileId` and `imgStoreId`, and appliance events `family`, `item` and `state`. Plain on/off and number changes are device values, not events: trigger on those with the `device` signals.

Activity feed for any signal: a signal kind marked `feed` in `read_signals` (plugin events by default, hub notices such as `storm`) is also recorded once as a `list_events` row of kind `signal`, with `details` source, kind, field, label, subject, value, `profileId` when it belongs to one person and `data` when it has any. Narrow those rows with `list_events` `source` (the signal source, for example `hub` or `plugin_router`) and `signalKind`; a person's AI sees only their own rows. A plugin author can set `feed: false` on a manifest event to keep it out of the feed; it still triggers automations.

Wake, listening and calls: the `listening` signals `wake_heard` (once per settled wake contest; `subject` the winning camera, phone, computer or channel id, or `discord`; `value` its loudness in dBFS; match `source`, `winner` and `decidedBy` only, capped at 6 a minute with a burst of 3 per source) and `state` (per listening source: `value` is `on`, `off`, `paused:<reason>`, `budget_used_up`, `mic_permission_lost`, `no_host` or `offline`; match `state`, `source` and `reason` privacy, in_call, discord_call or no_openrouter_key; camera transcript pauses are not reported) and the `call` signals `started` and `ended` (`subject` and `profileId` the person; match `source` chat, orb, palette, assist, assistant, shortcut or hosted, plus `person` and `device`; `ended` also `ending` and its `value` is the length in seconds, so test `gt` with 600 for calls over ten minutes) and `outreach` (`value` and match `state`: ringing, answered, declined, missed, failed or sent, plus `how` and `target`; trigger on `ringing` then `missed` to catch an unanswered AI call). All of them are recorded as `signal` rows in `list_events`, `started` and `outreach` survive a flood, none carries what was said, and the owner can switch the `listening` or `call` source off with `updateTriggerSettings`.

People arriving and leaving: the router plugin's signals `person_arrived` and `person_left` (source `plugin_router`, `subject` the person's name; match `name`, `person_id` and `profile_id`) fire once when a person's first linked device or paired phone shows them home, and once when the last one has been gone past the router's grace period. They are recorded in `list_events` like any plugin signal and capped at 6 a minute per person. As a condition, the router device has `raw:people_home` (how many are home) and one boolean `raw:home_<person id>` per tracked person (person ids come from `who_is_home`), readable with `get_device` and usable in `compare` like any control. Presence never selects the server route.

Flood protection: every signal source has a rate cap per device, field or kind, and a signal repeating faster than its cap is dropped, so never build a trigger on a continuous reading by itself: use a window (avg, min, max, count), a comparison with `hold`, or a crossing. Excess is logged and the `hub` signal `storm` (match `source`, `kind`, `reason` cap or global) tells the home when it happened; alarms and rings (`urgent` kinds) survive a flood. The owner switches a whole source or one `source/kind` off, or on for opt-in kinds (`optIn`), with `call_operation` `updateTriggerSettings` (`sources`: name to true or false, `kinds`: `source/kind` to true or false, null restores the default); `get_settings` shows `trigger_settings`, and an off kind drops its signals without a trace, so check it before blaming a trigger that never fires.

Commands and service connections: every command sent to a device is a `device` signal `command` (`subject` the device, `field` the control key, value what was sent) with match `status` (`sent`, `done`, `failed`, `timed_out`), `capability`, `cause` (`app`, `assistant`, `automation`, `scene`) and, when it failed, `error`; only `failed` and `timed_out` reach the activity feed (`list_events` kind `signal`), so trigger on `sent` or `done` for the rest. A connection to a service (Xiaomi, Tuya, SmartThings, Samsung TV, local) is the `provider` signal `status` (value and match `state`: `linked`, `attention` when it needs signing in again, `down` when it cannot be reached; also `provider`, `problem`, `error`). Each outage and each new adapter failure is one `provider_error` event, never one per device: while a service is in `attention` or `down`, its devices' `device_offline` and `device_online` events are not recorded, so read the `provider` status instead (the device itself still shows offline).

Device values, online and lifecycle: every `device` signal `state` also carries the facts of its device as match keys, so one trigger covers a whole group with no device list: `family` (light, fan, lock, computer, ...), `kind`, `roomId`, `provider`, `name`, `role` (what the value is, shared across models, such as `power`, `brightness`, `fault`), `unit` and `cause` (`physical` when someone used the device itself, `app`, `assistant`, `automation` or `schedule`, read from the command that preceded the change). Any light turning on in the Study is `match` family light and roomId of that room, `field` `power`, test `{is: eq, to: true}`; only a wall switch flip is `cause` physical. A value turning unknown is a signal with value null (an alarm cleared, playback stopped); the first value a device ever reports is not a signal. Numbers are announced only when they moved by at least the control's step and at most every 2 seconds (every 10 seconds for graphed readings such as latency), and the newest value follows when that pause ends, so use a window or `hold` for slow drift. `device` signal `online` (value true or false, every device including a computer, match the same facts; the activity feed keeps `device_online` and `device_offline` events) gives `hold` of 10 minutes on `eq` false for offline for ten minutes. `device` signal `lifecycle` is a moment with match `change`: `added`, `removed`, `renamed` (data `from`, `to`), `moved` (room), `replaced` (other hardware, `from`, `to` model), `capabilities_changed` (`added`, `removed` control keys) and `firmware_changed`; it reaches the activity feed as `signal` rows. Renames and moves the person makes in the app are not lifecycle signals.

Water bottle events: a LARQ bottle sends `activity` events whose `activity` is drink, refill, uv_clean, goal_reached or drinks_imported (a drink carries `ml` and `levelMl`; imported drinks older than 30 minutes arrive as one drinks_imported event), a `fault` event with the `fault` code and `name`, and `maintenance` events whose `maintenance` is battery_low or filter_due. Its `water_level`, `bottle_volume`, `battery`, `bottle_charging` and `bottle_state` are `device` state signals and conditions (no node reads the day's water total, so use the bottle level or the goal_reached event). Nodes can set `reminder_colour`, `reminder_interval`, `quiet_hours` and the window times (applied when the bottle next wakes) and `uv_clean` stop; an automation can never start a UV clean.

Treadmill events: a WalkingPad sends `activity` events whose `phase` is started, paused, resumed, finished or goal_reached (match `walker`, `kind` walk, jog, run or intervals, `goal`; the finished event also carries `distance_m`, `duration_s` and `steps`, which are read with `list_events` and cannot be matched), a `fault` event with the `code` (E01 to E13, or safety_stop), a `maintenance` event with `reason` lubrication_due, and a `button` event with `button` up, down, stop or mode. Its belt state, speed, mode and child lock are `device` state signals (use `hold` or a crossing for speed). A `device.set` node that starts the belt or raises its speed is refused like any remote start unless the owner allowed remote start, so keep stop and pause nodes for safety automations and tell the person when a start node will be refused. A Kingsmith G15 also has `belt_incline` as a `device` state signal and condition (the belt's own number, whole steps): trigger on it only with a `gte` or `lte` test, `hold` and `rearm` for hysteresis (for example `gte` 8, `rearm` 6, `hold` of 20 seconds), never on every change. A `device.set` node on `belt_incline` is refused unless the owner allowed remote incline, only raises up to the remote cap, and never runs while nobody walks, so do not build an automation that depends on it. The hub raises `goal_reached` only for the goals the belt supports today (distance, calories, time); there is no climb target event yet, so do not promise a notice for a reached climb target. There is no power off or standby step.

Toothbrush events (Philips Sonicare and Oral-B): the brush sends an `activity` event when a brushing is saved, with `brushing` finished (match `complete` true or false for a whole routine, `person` by name, `mode` and `durationS`), a `maintenance` event whose `brushHead` is warn or due when the brush head wears out, and a `fault` event with `brushFault` (error bits in hexadecimal). Its `brush_activity` (asleep, standby, brushing, paused, charging, off), `brush_mode`, `battery` and the head figure (`brush_head_wear` on a Sonicare, `brush_head_days_left` on an Oral-B; use a crossing) are `device` state signals and conditions. Activity and pickup changes are seen only while the brush's adverts reach a phone, so a trigger on them can be late. A `device.set` node can change the mode (and, on a Sonicare, intensity and the feedback switches) only on a handle that writes, with the owner's consent, and while it is awake and not brushing; it never starts a brush.

Printer events: the printer plugin is the signal source `plugin_printer`. Its kinds are `job_started` and `job_finished` (match `result` such as completed, canceled or aborted, plus `person` and `pages`), `problem_added` and `problem_cleared` (match `keyword` such as media-jam-error, `severity` and `part`), `alert`, `supply_low`, `supply_empty` and `supply_replaced` (match `supply` and `key`; the level is in the data), `restarted`, `config_changed`, `pairing_problem` (match `reason`) and `offline_long` (30 minutes without an answer). Every event carries the printer name in `printer` and its id in `printer_id`; match `printer` to pick one printer. Low and empty events follow the owner's notification switches and the low threshold set on the printer, and a flood is capped. Its state, queue, pages today, supplies and trays are `device` state signals.

Speech triggers (`trigger.speech`) match literal words or a contiguous phrase of finalized speech. `list_speech_sources` shows the cameras, plugins and chats that can be chosen; leave `source` out for every authorized source. Bot speech is ignored unless `includeBots` is set. Only the person who saved a speech automation may change it.

## Nodes and wires only

An automation is a flow chart of nodes joined by wires. Formulas, expressions and text templates do not exist anywhere: a port that needs a worked out value gets a wire from the output of a node that works it out. Build every program this way, step by step:

1. Every port, branch condition, case condition, structured output, variable start value and `admit` holds exactly one of two things: a constant `{"lit": value}` or a wire `{"wire": {"from": "<source>", "port": "<output>"}}`. Nothing else is accepted.
2. A wire's `from` is the `key` of a node that comes earlier (a loop or try gives `item`, `index` or `error` to the steps inside it), or one of five sources: `trigger` (the outputs of the trigger that fired, plus `key` and `at`), `inputs` (the inputs of a Custom Node or called automation), `vars` (a variable, by name), `home` (`timeZone`, `name`, `latitude`, `longitude`) and `run` (`id`, `startedAt`). `port` is one output name. To read a field inside a record, wire the record into Get field (`object.get`) and wire on from its `value`.
3. Work values out with calculation nodes. They never act, and can sit anywhere before the node that reads them: Compare (`logic.compare`: equal, not equal, greater, at least, less, at most), `logic.between`, Is one of (`logic.in`), And and Or (`logic.and`, `logic.or`: two to four flags wired into `a`, `b`, `c`, `d`), Not, Has a value (`logic.exists`), First available (`logic.coalesce`, with a `default`), Choose (`logic.select`: `condition`, then `whenTrue`, else `whenFalse`), Which trigger (`logic.trigger_is`), Add, Subtract, Multiply (two to four values in `a` to `d`), Divide, Remainder, Round, Clamp, Message (`text.format`: a fixed `template` whose `{a}` to `{d}` are filled from the values wired into `a` to `d`), Text check (`text.test`: contains, starts with, ends with, equals, is empty), Join, Count items (`list.length`), Get item (`list.get`: first, last or by index), Any item, Every item, Keep where and Find (`list.any`, `list.all`, `list.filter`, `list.find`: each compares every item, or one `field` of every record, by `test` with `value`), Field of each (`list.field`), Get field, Convert (`util.convert`: to number, text, on/off, duration, moment or list) and Lookup table (`util.lookup`).
4. Decide with wires too: an If branch `when`, a switch case `{"when": ...}`, the wait-for-condition `condition`, `admit` and the `condition` of `trigger.becomes_true` each take a wire to a flag, usually the `result` of a Compare, And, Or, Not or Has a value node. A switch on a value takes the wire in `subject` and fixed cases (`eq`, `in`, `range`).
5. An optional output (optional in the catalog) cannot feed a port that needs a value: test it with Has a value and branch, or pass it through First available with a `default`. A number wire fits any number port; for another type wire it through Convert.
6. Effects (device commands, notifications, tool calls, Value and variable changes) are always their own nodes on the run path, never inside a calculation.

Example: lights to step 1 when the step is 0 or no light is on. `stepIsZero` is a Compare with `a` a wire from `vars` port `step`, `op` eq and `b` 0; `noneOn` is a Compare with `a` a wire from `onNow` port `count` and `b` 0; `either` is an Or with `a` wired from `stepIsZero` port `result` and `b` from `noneOn` port `result`; the `flow.if` branch `when` is a wire from `either` port `result`.

Per-room logic is one Custom Node, never copies. Give it inputs for what differs per room (for example `lights` a target, `event` a choice, `sensors` a list of devices, `allowed` a flag), keep what it must remember in `persist` variables, and build its body from the nodes above. Each room's automation then holds its triggers and one `fn.call` with the room's constants and wires, for example `event` wired from a Lookup table or Choose fed by a wire from `trigger` port `key`. Change the Custom Node once and every room follows.

## Writing programs

- Keep ids and keys on every update: copy the stored program, change only what the person asked and leave node ids, keys and unrelated nodes as they are, so the editor, run history and breakpoints stay attached. Give a new node a short readable `key` and leave its `id` out.
- Prefer `edit_automation` action `patch` (ordered operations with `expectedRevision`, one revision) for a change; use `update` with the whole program only for a rewrite. Read the program (`list_automations` view `full`, or `outline` for one keyed line per node) and pass its `revision` as `expectedRevision`; after a refusal read again and edit on purpose.
- Before saving a new automation run `edit_automation` action `check`, fix every problem it lists (each names the node, port, code, expected, received and a fix), then `run_automation` with `mode` `dry`: it records the commands it would send without sending anything. `mode` `simulate` replays a scenario (fixtures, start time, a timeline of signals and time advances) on a virtual clock; timeline signals wake waits, they do not start triggers. Both start as a manual run unless `trigger` gives the `key` of one trigger, and optionally its `signal` (source, kind, subject, field, value, previous, profileId, data), to start as if that trigger fired, so test each trigger of a program that branches on the trigger `key`. Save and enable only after both look right.
- Literals: a port for one device, room, person, Value or Custom Node takes the plain id; a `target` port takes `{"device": id}`, `{"devices": [ids]}`, `{"room": id, "families": [...]}` or `{"group": id}`. A `target` port also takes a wire from any output that gives a device or a list of devices (for example the `devices` output of Find devices), and the command goes to every device in the list.
- Repeated per-room or per-device logic is one Custom Node placed once per room with its inputs set, never copied; change the Custom Node once for every caller. A save that breaks callers lists them and needs `confirmBreaking` true: show the person that list first.
- An action Custom Node can keep data for each place it is used: give one of its variables `persist` true, read it with a wire from `vars` and its name or with `var.get`, and change it with `var.set` or `var.change` with `source` automation. Every use keeps its own copy (a use inside another Custom Node too), separate per automation, kept through hub restarts and removed when that step is removed; each change is saved on its own, so a run that fails later keeps the changes made before. A calculation Custom Node cannot keep data. When the kind of kept data changes, data that still fits stays and data that does not starts again from its start value with a note in the activity. Detaching a use copies the steps and its kept data starts again.
- Prefer waiting on the event or condition (the wait-for-event and wait-for-condition nodes of the `flow` group) to loops that poll, and a trigger to a loop that waits for a change.
- Secrets (API keys, tokens) never go in a program or chat history. The owner stores one with `edit_automation` action `set_secret` (name and write-only value); a node refers to it by id in the `auth` port of `http.request`. `list_automations` view `secrets` shows names, dates and users, never values; `remove_secret` deletes an unused one. Literal `authorization`, `cookie` or `x-api-key` headers are refused.
- Member scope: a member's AI reads and changes only that person's own automations and uses only their own devices and computers; `ai.wake`, `tool.call`, `http.request`, secrets and file nodes are owner only and are refused when saved by anyone else.
- The editor keeps three per-person preferences you read with `get_settings` view `app` and change with `update_settings` action `preference`: `automations_editor` (the view each device class opens, `auto`, `canvas` or `outline`, and whether the moved-automations note was closed), `automations_palette` (recent and favourite node kinds) and `automations_breakpoints` (step ids per automation where a dry run pauses). Change them only when the person asks, and send the whole `view` or `byAutomation` value because a write replaces that field.

## Triggers and timing

Triggers are entry nodes: `trigger.device` (one device or a whole room, group or family), `trigger.signal`, `trigger.time`, `trigger.interval`, `trigger.sun`, `trigger.speech`, `trigger.presence`, `trigger.camera`, `trigger.button`, `trigger.called`, `trigger.value`, the run-status trigger, the device-health trigger and the eleven later ones listed below; the catalog lists each one's outputs, and a node reads them with a wire from `trigger` and the output name, together with the ports `key` (which trigger fired) and `at`. A device or signal trigger takes a `test` (`eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `between`, `in`, `changed`), a `window` (average, min, max, count or rate over a time) and these timing ports, all durations unless noted:

- `hold`: the test must stay true that long. `debounce`: decide only after no new signal for that long. `cooldown`: fire at most once in that long.
- `silentFor` (1 second to 7 days) fires when no matching signal arrived for that long, for example no motion in the hallway for 2 hours; it starts counting when the automation is enabled, every matching signal restarts it, it survives a hub restart, fires once per silence, and takes only `cooldown` besides it.
- `first` (`day`, `week` or `ever`) lets only the first match in the home day, the home week (Monday start) or ever fire, remembered across restarts; a match held back by `cooldown` does not use it up.
- `rearm` is a number for hysteresis on a `gt`, `gte`, `lt` or `lte` test: after firing on `gt` 28 with `rearm` 26 it fires again only after the value went below 26 (for `lt` and `lte` above it); `rearm` lies on the far side of the test value.
- `ignoreOwnChanges` (on by default) keeps an automation from triggering on its own commands; leave it on unless the person wants the loop.

The later triggers:

- `trigger.becomes_true` takes a `condition` (a wire to a flag from the read and calculation steps at the very start of the program) and an optional `hold`. It is checked only when something the condition reads changes, never on a timer, and fires on the change from false to true: not when the condition is already true as the automation is saved or the hub starts, and with `hold` only after it stayed true that long. A condition that fails, for example on a missing value, counts as false and the reason is logged.
- `trigger.computer` (`computer`, `kind` `app_open`, `app_focus`, `app_close`, `app_unfocus`, `power` or `power_<action>` such as `power_lock_screen`, plus `app` and `title`), `trigger.phone` (`phone`, `kind` `unlocked`, `context_changed` or `parked`, plus `to` and `from` for a change of activity), `trigger.health` (`kind` `sleep_ended`, `body_reading`, `today` or `logged`, plus `person`, `metric` and the timing ports) and `trigger.chat` (`chat`, `outcome` `answered` or `failed`) start on what the hub already sees.
- `trigger.weather` starts the moment new weather arrives and something changed (no change, no start; the feed refreshes every 15 minutes, the step of the provider's current data). `event` is `changed` (a `metric` such as temperature, feels_like, humidity, precipitation, wind_speed, uv_index or aqi, with a `test` and, to fire once per crossing, `rearm` a little past it on the other side, for example test above 25 and rearm 24), `band` (a `metric` moving into another band, `to` and `from`: temperature and feels_like freezing, cold, cool, mild, warm or hot; humidity dry, comfortable or humid; precipitation none, light, moderate or heavy; cloud_cover clear, partly_cloudy or overcast; wind_speed calm, breezy, windy, gale or storm; uv_index low, moderate, high, very_high or extreme; aqi good, fair, moderate, poor, bad or severe), `condition` (`to` and `from` clear, partly_cloudy, cloudy, fog, drizzle, rain, snow or storm), `rain_started` (optional `falling`), `rain_stopped`, `rain_expected` (`within` 15m, 30m, 1h, 2h, 3h or 6h, judged from the hourly forecast) or `forecast` (every update). For rain use `rain_started` and `rain_stopped`, never a polling interval with a weather read.
- `trigger.event` starts on the `signal.emit` step that sends the same `name`; `trigger.timer` starts when the Timer step of that `name` ends, also when the hub was down at the time; `trigger.hub_started` starts once each time the hub starts; `trigger.schedule` starts at each block of a weekly plan.
- `trigger.webhook` is for owners. Its `path` is the secret: 16 to 128 letters, digits, dashes or underscores, and the address is `/hooks/<path>` on the hub (GET, POST, PUT or DELETE, or the one `method` chosen). The run reads `trigger.method`, `trigger.body`, `trigger.headers` and `trigger.query`. An `http.respond` step answers the caller; without one the caller gets 202 as soon as the run waits, or 204 when it ends, and 500 with the reason when it fails.

## Nodes

Common nodes: `device.set` (`target` device, devices, room or group; `control`; `to`; `percent`; `by` adds to a number), the temporary-set node of the `device` group (the control returns to its base after a time, when its `while` condition turns false, or when stopped; `priority` orders overlapping changes), `device.get`, `scene.run`, `flow.if`, `flow.switch`, `flow.repeat`, `flow.while`, the for-each loop, `flow.wait`, the wait-for-event and wait-for-condition nodes of the `flow` group, `notify.person` (really pushes), `notify.feed`, `notify.speak`, `var.get`, `var.set` and `var.change` (Values and variables), `automation.run`, `automation.stop` and `fn.call` (a Custom Node). A run keeps going when a scene or automation it uses is edited. Loops have no limit unless one is set: `flow.repeat`, `flow.while`, `flow.do_until` and the loop-until-break node `flow.forever` take an optional `limit` (`iterations`, `time` in ms, `onLimit` fail or end, optional `note`), the for-each loop runs any number of items at once with `concurrency`, and the automation's `budgets` (steps in a row, steps per run, loop passes, run chain length, side-by-side branches) are optional too; only `commandsPerMinute` (600) and the run state size guard (`runStateBytes`, 8 MiB) have defaults. A run never blocks the hub and `stop_automation` ends it at any time. A `flow.forever` needs a Break, Return or Stop inside or a `limit`; the checker names what a loop lacks.

`computer.audio` (`computer`, `change`) takes the `set_computer_audio` action and its fields, such as `app_volume` with `app` and `level`, `app_mute`, `app_output`, `volume`, `mute` or `default`. `computer.display` takes `change` `mode` (`output`, `width`, `height`, optional `refreshHz`), `scale`, `position`, `brightness` or `night_light`; HDR, rotation, main screen and turning screens off or mirroring them stay with a `tool.call` node. Read `get_computer` first for the exact names and the features the computer offers; a node the computer does not offer, a device that is not a computer, or (for a member) someone else's computer is refused when saved. Nobody is asked while it runs, so a screen change that can blank a screen (`mode`, `scale`, `position`) goes back by itself after 15 seconds unless someone keeps it at the computer. Add `keep: true` to keep it automatically once the hub has read the screen back and seen the change applied; if it does not match, the change is reverted at once and the node fails.

The run policy `mode` is single (default), restart, queue or parallel; queue needs `max` (and may take `maxWait`), parallel may take one. `key` names runs so `stop_automation` can end only those. Custom Nodes (`fn.call`) may call themselves or each other: recursion is allowed with no depth limit, and a runaway recursion is stopped by `stop_automation` or fails when its run state grows past `runStateBytes`. An `automation.run` node refuses to start an automation already in its own chain of runs unless it sets `allowSelf`.

`ai.wake` (`person`, optional `chat`, `instruction`) wakes that person's AI with what happened. `tool.call` (`person`, `tool`, `args`) calls any enabled tool without an AI turn, using the exact arguments from `tool_details`; for example `speak` with `{"target":{"kind":"device","deviceId":"<camera id from read_presence>"},"text":"Exact words"}` says words once through a camera speaker. Both are for the owner; the editor offers them too, plus a ready "Say out loud" node for camera speakers, so anything you build the person can open and change. Old tool names still work.

Every automation records who made it in `author` (`via` person or assistant, and `profile_id`), and a plugin in `origin`; `author` is null only for automations made before this was recorded. Never create, change, switch, run or remove an automation the person did not ask for, and never touch one only because it looks wrong: say what you noticed.

## Integration nodes

Read the node catalog (`list_automations` view `catalog`) for exact ports. `ai.ask` runs one model call for a person and returns `text`, `result` (when a `shape` is given), `tokens` and `cost`; it has no tools unless `tools` names them, so give it tools only when none of its inputs come from outside the home. `ai.vision` does the same on pictures or a `camera` (the Bedroom camera stays blocked) and `ai.decide` returns a yes or no `answer` with a `reason`. A member's AI call runs as that member and stops at their budget. `camera.snapshot` stores a picture and returns its id for later `ai.vision` calls. `computer.power`, `phone.action`, `health.read` and `signal.emit` act on a computer, a phone, the person's health data or the signal bus; `http.respond` answers the webhook that started the run, once.

## More nodes

All of these are in the catalog; read it for exact ports. Pure ones only compute and never send anything.

- Devices: `device.snapshot` (Remember state) reads chosen controls of the target and `device.restore` puts them back, skipping offline devices and saying which. `scene.capture` saves the current values of devices as a scene (`overwrite` must be on to replace one of the same name). `device.fade` moves a number control (brightness by default) from one level to another over a time, paced by the command budget; stopping leaves it at the current level. `device.ensure` sends a value, waits for the device to report it and sends again if it does not, for devices whose cloud drops commands. `device.ir_send` presses a button of a learned infrared remote through its blaster.
- Readings: `computer.read` and `phone.read` return what a computer or phone reports now (a figure it does not report is left out), `signal.latest` reads the newest signal of one kind since the hub started (it never wakes a wait: use the wait-for-event node for that), `weather.forecast` reads the next hours (rain chance, wet hours, lowest and highest temperature, strongest wind) and `date.sun_times` gives sunrise, sunset, twilight, solar noon and golden hour (absent when the sun does not reach that day; fails when no home location is set).
- Flow: `flow.sequence` (Steps) only groups steps under a name for readability. `flow.forever` repeats until a Break, Return or Stop. `debug.breakpoint` (Pause here) pauses a dry run or simulation until the person continues.
- Logic: `logic.and`, `logic.or` and `logic.not` combine flags, `logic.changed` tells whether a value differs from the last run of this node in this automation (the first run counts as changed), `logic.count_true` counts true flags against `atLeast` and `atMost`, `logic.xor` is true when exactly one flag is, `logic.day_type` tells weekday, weekend or one of the dates you list (no holiday calendar is built in), `logic.in_schedule` tells whether a moment falls in weekly slots (a slot that ends after midnight belongs to the day it starts on).
- Numbers and chance: `math.convert_unit` converts within one kind of unit (temperature, length, power, energy, pressure, speed, colour temperature, volume), `math.percent` gives a percent of, a percent change or a percent value (a zero base fails), `random.chance` is true with a probability from 0 to 1 and `random.duration` picks a duration between a minimum and a maximum; random results are captured for the run and a simulation can seed them.
- Text: `text.case` trims, changes case or makes a slug, `text.slice` cuts, shortens with an ellipsis and pads, `text.speakable` writes a number, duration or moment the way it is said aloud (numbers and durations are English).
- Lists: `list.range` (numbers from one to another in steps), `list.slice` (a run, the first N or the last N), `list.sort` (numbers or texts, or records by a `field`; mixed kinds fail), `list.unique` (optionally by a `field`), `list.combine` (join, union, intersection or difference) and `list.reshape` (reverse, flatten one level, chunk or zip). To work through a list item by item use the for-each loop with `collect`, or `var.change` inside it to add up.
- Records: `object.fields` takes a record apart into keys, values and entries or builds one from entries, `object.merge` (a later record wins; `deep` merges inside records), `object.pick` keeps or omits listed fields and `object.remove` drops the field at a path (a missing path fails unless ignored).
- Time: `date.next` is the next moment a time of day comes round on chosen weekdays (daylight saving handled) and the start-of node of the `date` group is the first moment or last millisecond of a day, week (Monday), month or year in the home time zone.
- Secrets: `var.secret` hands a stored secret to a node that accepts one, such as the `auth` of `http.request`; its value is never shown, recorded or readable as text. Owner only.

## Memory and questions

Some nodes remember between runs, per automation and across hub restarts. `timing.cooldown` lets a run pass at most once per `period` (an optional `key` counts per room or device) and sends the others out of its `blocked` exit. `timing.debounce` continues only the newest run after `quiet`; older ones leave by `superseded`. `timing.rate_limit` lets `max` runs pass per `window` and sends the rest out of `dropped`, or with `excess` queue holds them for the next free slot. `timing.quiet_hours` holds a run until a daily window (`from`, `to`) ends, or sends it out of `held` when `quiet` is skip, unless its `priority` reaches `bypass`. `timing.hysteresis` switches high and low on two thresholds and reports `rose` and `fell`. `state.counter` counts up or down, resets, sets, wraps, resets every day, week or month, or counts only a recent `window`. `state.machine` keeps one mode and moves it by events. `state.timer` starts, restarts, extends, pauses, resumes or cancels a timer by `name` (`trigger.timer` fires when it ends). The first exit simply continues after the node; the other exits are lanes of the node (`blocked`, `dropped`, `held`, `superseded`, `timedOut`), and without a lane the run stops quietly there, like a guard.

`notify.ask` asks a person (`person`, `question`, two to four `options`, optional `timeout`) and keeps the run waiting, also across a restart. It returns `answer`, `by` and `timedOut`; with `defaultAnswer` a time out answers for the person, otherwise `answer` is missing and the `timedOut` lane runs. The question arrives in the person's chat and shows under Automations with its buttons. `read_automation_runs` view `questions` lists what waits and `answer_automation_question` presses a button; use it only when the person told you which one. In a simulation the timeline entry `{at, answer}` presses a button. `builtin.ask_then_act` is a ready Custom Node that asks a yes or no question and leaves by `yes`, `no` or `timedOut`.

## Values

`edit_value` creates, replaces, removes or applies an operation (set, toggle, add, subtract, next, previous). Apply an operation for any change; never read a Value and write a calculated replacement. Replacing needs the current `revision` as `expectedRevision`; a Value or choice that an automation uses cannot be removed.

## Running and checking

Saving a program proves it is valid, not that the trigger fires. `run_automation` in `live` mode skips triggers and the admit condition and really performs the nodes, so run it only when the person wants that; pass `inputs` for one that declares them and `wait` to get the outputs. `run_scene` and a scheduled action's run also act immediately.

`read_automation_runs` view `list` gives recent runs, view `run` one run with node outcomes, value previews, loop counts, errors and linked command ids, view `nodes` pages the node records of one run (filter by node or loop iteration) and view `decisions` says why an automation did not run (admit false, cooldown, storm protection, a refused start). Statuses: queued, running, waiting, paused, cancelling, cancelled, succeeded, failed, interrupted, ignored. `stop_automation` ends one run (`action` run) or all runs of an automation, optionally one `key` (`action` automation); commands already sent may finish. A waiting run resumes after a hub restart; one interrupted by a restart in the middle of a short step is not resumed. Last run and error are in `list_automations`.

A `device.set` node to a room or group skips offline or unsupported members and says which; it fails when nothing could be sent or a command was refused or left uncertain. Check the linked commands before repeating anything whose physical outcome is unknown.

Active temporary changes are listed by the `listDeviceEffects` operation (`list_operations`, `call_operation`) and one is ended with `endDeviceEffect`. Use `show_widgets` with returned scene, automation or schedule ids to let the user open the result.
