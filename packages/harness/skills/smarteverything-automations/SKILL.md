# Scenes, automations and schedules

Checklist before saving anything, because an automation acts on the home without anyone watching:

1. Change only what the person asked for; suggest other automations in words.
2. Read `automation_read` view catalog for node kinds, ports, run modes and plugin nodes, `device_read` for every control, `signal_read` view catalogue for triggers.
3. `automation_edit` action check, then `automation_run` mode dry, read the result, then save or enable.
4. Report what it will do, when, and what you could not express.

## Choose the mechanism

- A scene is a flat list of device commands: `scene_find`, `scene_edit`, `scene_run`.
- An automation is a program of connected nodes: triggers that start it, then logic and first-class nodes for devices, people, computers, phones and plugins. Look in the catalog for the node that does the job before reaching for `tool.call`. `automation_read` reads, `automation_edit` writes. A program with a `trigger.called` entry and no other trigger is started by `automation_run` or an `automation.run` node; declare its inputs there.
- A Custom Node is the same kind of program with an interface (inputs and outputs) that other programs place as a node, for example one per-room routine. It is read with `automation_read` view `functions` and written with `automation_edit` like an automation.
- Every hub starts with six Custom Nodes made of ordinary nodes; everyone can open them and an owner can change them: Say it, or push it; Switch devices; Lights off after no motion; Flash the lights; Wake-up light; Leave home check. Find their ids with view `functions`, reuse them with `fn.call` before building the same steps again.
- A Value is a named on/off, number, duration or choice that nodes read and change: `value_read`, `value_edit`. A variable owned by one automation lives in its program, not in `value_read`.
- A one-off action for later is `schedule_find` and `schedule_edit`. Update the matching item instead of creating a duplicate.

Read the home time zone with `home_read` for clock times. Keep the user's timing and target scope; ask only about ambiguity that changes what runs or when.

## Writing programs

A program is nodes and wires. A value wire feeds data into a port: `{"wire": {"from": key, "port": name}}`. The order of a run is set by where each step goes next, written as `to` on the node the run leaves: `{"to": {"next": "other_key"}}`. A port left unwired ends that path.

- Every program has one `flow.start` node; its `next` is the first step. Triggers start it and need no wire. An automation can have one `flow.on_failure` node: the steps after it run when a run fails. Neither is in the catalog; copy them from the program you read, or write them in a new program.
- Where each kind goes next: a step `next`. If a `to` on each row of `branches` plus `else`. Switch a `to` on each row of `cases` plus `default`. Only continue if `next` and `otherwise`. A loop `body` (each pass) and `next` (when done). Try `try`, a `to` on each row of `catches`, `finally` and `next`. Do together a `to` on each of its `paths`; every path leads into the one `flow.join` (Wait for all), whose `next` carries on. A wait with a `timeout` also has `timedOut`, and every step the catalog marks `fallible` has the If it fails exit `onError` (wire it to the steps that handle the failure; they read `reason`, `message` and `code` from the failing node). Stop, Return, Raise error, Break and Next item have no exits.
- Paths meet by naming the same node: two rows of an If that both go to `notify` run it once, after whichever row was taken. Put the steps that follow a decision after the node its paths meet at, and end a path early by leaving its port unwired.
- Every automation and Custom Node has a `description` of one short plain line: what starts it and what it does, for example `When the baby cries in the bedroom: tell the owner, pause the bedroom TV and blink the lights that are on red.` No device lists, ids, timings or step by step detail; that lives in the program. When the behaviour changes, rewrite the line with `header` (or in the full program) in the same change.
- Keep ids and keys on every update: copy the stored program, change only what the person asked and leave node ids, keys, row ids and unrelated nodes as they are, so the editor, run history and breakpoints stay attached. Give a new node a short readable `key` and leave its `id` out; a `to` names a key.
- Prefer `automation_edit` action `patch` (ordered operations, one revision, all or nothing) for a change, and read the program first with `automation_read` view `outline`: one line per node in run order with its wires, such as `turn_on · Set Kitchen lights brightness to 80 % → then wait_1` or `if_dark · If · yes(Is it dark) → lights_on · otherwise → notify`. A draft whose wires do not form a valid graph is listed in stored order under "Not a valid graph yet" with its problems. View `full` gives the whole program with row ids; use `update` with the whole program only for a rewrite, or with only `enabled` to switch an automation on or off. The hub applies a patch to the revision it holds now.
- Patch operations: `add` a node, and with `after` {key, port} it goes into that wire (that port now goes to the new node and the new node `next` goes to the old target; for a decision, loop or Try give the new node its own `to`). `connect` {from, port, to} and `disconnect` {from, port} change one wire. `set` changes ports, `policy`, `mode` and `timeout` (the run mode and how long a waiting step waits, each cleared with null), `label`, `note`, `enabled` or the `outputs` (values after an If, Switch, Try or Do together), `unset` clears ports, `rename` changes a key everywhere it is used. `remove` takes a node out; with `heal` the wire that led into it goes to where it led on, and `cascade` clears ports that read its values. `row` adds, removes, moves or edits a branch, case or catch row (a new row may carry `to`), `path` adds, renames or removes a Do together path, `wrap` puts a chain of steps with one way in and at most one way out inside a new If, loop, Try or Do together, and `header` changes variables, inputs, outputs, policy, admit, budgets or description. Connecting from the port `onError` wires the If it fails exit and makes the step route its failures there; disconnecting it restores the previous policy, and every inverse operation puts the previous mode, timeout and policy back. Name a row exit in `connect` as `row:<id>`, `case:<id>`, `catch:<id>` or `path:<name>`; other exits by their name (`next`, `else`, `default`, `body`). Adding a Do together adds its Wait for all with it.
- Before saving a new automation run `automation_edit` action `check`, fix every problem it lists (each names the node, port, code, expected, received and a fix; a wire problem names the nodes and the wire), then `automation_run` with `mode` `dry`: it records the commands it would send without sending anything. `mode` `simulate` replays a scenario (fixtures, start time, a timeline of signals and time advances) on a virtual clock; timeline signals wake waits, they do not start triggers. Both start as a manual run unless `trigger` gives the `key` of one trigger, and optionally its `signal` (source, kind, subject, field, value, previous, profileId, data), to start as if that trigger fired, so test each trigger of a program that branches on the trigger `key`. Save and enable only after both look right.
- Order of evaluation: a step reads its input ports in port order when control reaches it, an If tests its rows top to bottom and stops at the first true one, a Switch reads its subject once, For each, Repeat and Count read their bounds once, and While and Do until read the condition on every pass. Effects happen only in the order of the wires (paths of a Do together run at the same time, each in its own order), while value nodes such as device reads and calculations run when something reads them, so where one sits never changes what the run does.
- Wire problems have a code and plain words that name the nodes. `wire_cycle`: the wires go round in a circle; use a loop node to repeat steps. `crosses_region`: a path leaves or enters a loop, Try or Do together body from outside; end the path inside it and let the run carry on after the loop, or wire it to a step outside. `shared_branch_node`: a step is reached from two paths that do not meet at it; make the paths meet at one step before it, wire Otherwise of an Only continue if to it, or combine two conditions with an Or node and use one If. `path_not_joined`: a Do together path ends before its Wait for all; wire its last step into it. `join_mismatch`: a Wait for all gets wires from steps that are not paths of its Do together; wire only that fork's paths into it. `exit_shape`: the other exit of a memory node must lead back to its Then step or end; wire it back or leave it unwired. `switch_all_early_end`: in match mode every, a case ends early; wire it to the step after the Switch. `never_runs`: nothing leads to a step; wire a `next` into it or remove it. `exec_into_start`: nothing can lead into Start or On failure. `unknown_target`: a `to` names a key that is not a step; pick one that exists. `loop_control_outside`: Break or Next item is not in a loop body; move it into the body.
- Literals: a port for one device, room, person, Value or Custom Node takes the plain id; a `target` port takes `{"device": id}`, `{"devices": [ids]}`, `{"room": id, "families": [...]}` or `{"group": id}`. A `target` port also takes a wire from any output that gives a device or a list of devices (for example the `devices` output of Find devices), and the command goes to every device in the list.
- Repeated per-room or per-device logic is one Custom Node placed once per room with its inputs set, never copied; change the Custom Node once for every caller. A save that breaks callers is still saved; callers keep following the last compatible revision and the reply lists them under `affected`: tell the person.
- An action Custom Node can keep data for each place it is used: give one of its variables `persist` true, read it with a wire from `vars` and its name or with `var.get`, and change it with `var.set` or `var.change` with `source` automation. Every use keeps its own copy (a use inside another Custom Node too), separate per automation, kept through hub restarts and removed when that step is removed; each change is saved on its own, so a run that fails later keeps the changes made before. A calculation Custom Node cannot keep data. When the kind of kept data changes, data that still fits stays and data that does not starts again from its start value with a note in the activity. Detaching a use copies the steps and its kept data starts again.
- Prefer waiting on the event or condition (the wait-for-event and wait-for-condition nodes of the `flow` group) to loops that poll, and a trigger to a loop that waits for a change.
- Secrets (API keys, tokens) never go in a program or chat history. The owner stores one with `secret_edit` action `set` (name and write-only value); a node refers to it by id in the `auth` port of `http.request`. `automation_read` view `secrets` shows names, dates and users, never values; `secret_edit` action `remove` deletes an unused one. Literal `authorization`, `cookie` or `x-api-key` headers are refused.
- Member scope: a member's AI reads and changes only that person's own automations and uses only their own devices and computers; `ai.wake`, `tool.call`, `lock.set`, `http.request`, secrets, file nodes and any plugin node marked owner in the catalog are owner only and are refused when saved by anyone else.
- The editor keeps three per-person preferences you read with `settings_read` view `app` and change with `settings_edit` action `preference`: `automations_editor` (the view each device class opens, `auto`, `canvas` or `outline`, and whether the moved-automations note was closed), `automations_palette` (recent and favourite node kinds) and `automations_breakpoints` (step ids per automation where a dry run pauses). Change them only when the person asks, and send the whole `view` or `byAutomation` value because a write replaces that field.

## Editor tasks

Everything the person does in the editor has a tool path:

- Row names: an If branch or Switch case row takes an optional `name` shown on its exit, for example `{"id": "<uuid>", "when": {"lit": true}, "name": "Evening", "to": "living"}`; the outline then reads `pick · If · evening(yes) → living · otherwise → study`. Rename one with `{"op": "row", "key": "pick", "edit": {"row": "branch", "t": "name", "id": "<row id>", "name": "Night"}}` (`row` case for a Switch, `name` null clears it).
- The Name field of a step is its `label` (`set` with `label`); the step key stays.
- Rename: `automation_edit` action `update` with only `name`; a name another automation or Custom Node already uses is refused with a plain message naming it. Duplicate: read view `full`, then `create` with a new name and `enabled` false.
- A Custom Node used twice is two `fn.call` steps with the same `fn` and their own input ports, for example `{"key": "living", "kind": "fn.call", "ports": {"fn": {"lit": "<id>"}, "level": {"lit": 80}}}` and `study` with 20. `custom_node_edit` action `extract` (`automationId`, `keys`, `name`) moves chosen steps into a new Custom Node and calls it in their place (the reply's `instanceKey` is the key of that new call); action `move_callers` (`functionId`, `mapping`) moves every caller onto its latest revision.
- History: `automation_read` view `revisions` lists published revisions, `revision` reads one, `compare` (`from`, `to` a revision or `draft`) says what differs. `automation_versions_edit` action `restore` (`automationId`, `revision`) publishes that revision again as the next one, with its layout. View `draft` shows the person's unpublished editor copy (`drafted`); `publish` and `discard` act on it only when the person asks. Your own edits publish directly.
- Tests: `automation_tests_edit` action `create` stores a simulation (`name`, `scenario`, `expectations` such as `{"kind": "status", "equals": "succeeded"}`, `command`, `output` or `visited`), `run` runs every stored test without sending anything; `automation_runs_read` view `tests` lists them.
- Layout and Tidy belong to the editor: new steps are placed by it, so never write layout.
- Not possible for anyone yet: detaching one use of a Custom Node into plain steps.

## Run mode and failures

Plain device commands (`device.set`, `light.set`, `scene.run` and the like) send and continue at once (`fire_and_forget`); reads and questions wait. In the catalog `modes` gives each step's default and what it allows. Choose `wait_for_result` when a later step needs the outcome or must not start before the device confirms (a read-back, an output marked `waitOnly`), and give it a `timeout`; a wait that runs out fails with `Timeout`. Every node that can fail has the If it fails exit: wire `onError` to a notify or a fallback so a failure is handled where it happens. A step with no wired exit behaves as its `policy.onError` says (`fail` or `continue`), and the `flow.on_failure` node still catches what is left.

## Memory and questions

Some nodes remember between runs, per automation and across hub restarts. `timing.cooldown` lets a run pass at most once per `period` (an optional `key` counts per room or device) and sends the others out of its `blocked` exit. `timing.debounce` continues only the newest run after `quiet`; older ones leave by `superseded`. `timing.rate_limit` lets `max` runs pass per `window` and sends the rest out of `dropped`, or with `excess` queue holds them for the next free slot. `timing.quiet_hours` holds a run until a daily window (`from`, `to`) ends, or sends it out of `held` when `quiet` is skip, unless its `priority` reaches `bypass`. `timing.hysteresis` switches high and low on two thresholds and reports `rose` and `fell`. `state.counter` counts up or down, resets, sets, wraps, resets every day, week or month, or counts only a recent `window`. `state.machine` keeps one mode and moves it by events. `state.timer` starts, restarts, extends, pauses, resumes or cancels a timer by `name` (`trigger.timer` fires when it ends). The first exit simply continues after the node; the other exits (`blocked`, `dropped`, `held`, `superseded`) are outputs of the node: wire one to a step to do something there, or leave it unwired to end the path there quietly, like a guard. `timedOut` of a wait is an output in the same way.

`notify.ask` asks a person (`person`, `question`, two to four `options`, optional `timeout`) and keeps the run waiting, also across a restart. It returns `answer`, `by` and `timedOut`; with `defaultAnswer` a time out answers for the person, otherwise `answer` is missing and the path wired to `timedOut` runs. The question arrives in the person's chat and shows under Automations with its buttons. `automation_runs_read` view `questions` lists what waits and `automation_answer` presses a button; use it only when the person told you which one. In a simulation the timeline entry `{at, answer}` presses a button.

## Values

`value_edit` creates, replaces, removes or applies an operation (set, toggle, add, subtract, next, previous). Apply an operation for any change; never read a Value and write a calculated replacement. `action` apply takes `operation` and `value` only (the hub knows the kind); a Value or choice that an automation uses cannot be removed.

## Running and checking

Saving a program proves it is valid, not that the trigger fires. `automation_run` in `live` mode skips triggers and the admit condition and really performs the nodes, so run it only when the person wants that; pass `inputs` for one that declares them and `wait` to get the outputs. `scene_run` and a scheduled action's run also act immediately.

`automation_runs_read` view `list` gives recent runs, view `run` one run with node outcomes, value previews, loop counts, errors and linked command ids, view `nodes` pages the node records of one run (filter by node or loop iteration) and view `decisions` says why an automation did not run (admit false, cooldown, storm protection, a refused start). Statuses: queued, running, waiting, paused, cancelling, cancelled, succeeded, failed, interrupted, ignored. `automation_stop` ends one run (`action` run) or all runs of an automation, optionally one `key` (`action` automation); commands already sent may finish. A waiting run resumes after a hub restart; one interrupted by a restart in the middle of a short step is not resumed. Last run and error are in `automation_read`.

A `device.set` node to a room or group skips offline or unsupported members and says which; it fails when nothing could be sent or a command was refused or left uncertain. Check the linked commands before repeating anything whose physical outcome is unknown.

Active temporary changes are listed by the `listDeviceEffects` operation (`operation_call`; `tool_read` gives its input) and one is ended with `endDeviceEffect`. Use `widget_show` with returned scene, automation or schedule ids to let the user open the result.
