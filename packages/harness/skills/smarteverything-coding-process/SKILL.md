# Coding

## Establish the project

Read the project's operating instructions and `STATE.md` before changing code. Inspect the relevant implementation, neighboring patterns, tools, skills, dependencies and checks. Reuse available mechanisms before creating replacements. A capability listed in a catalogue is not proof it works on the current execution host; discover actual schemas and readiness, and record missing equivalents without rewriting upstream skill instructions. At project start verify required integrations, project records, agent brief, automatic checks and test tools; use current-chat updates for missing input. Enable or install additional integrations only within the person's authorization.

Keep the selected harness and model. Coding does not automatically start or delegate to Claude, change an engine, or require a computer. Use actual available file, preview and agent tools; load `smarteverything-browser` when webpage reading, website testing or embedded-viewer diagnostics are needed.

## Files and execution

The selected machine is the execution target. Ordinary native `read`, `read_image`, `write`, `edit`, shell and job paths refer to that machine, following this chat's native permission and its actual OS account. Full access needs no extra project grant. Limited modes keep their native approval and sandbox behavior. An authenticated owner may use native Hub tools when Home Hub is selected; restricted accounts use their admitted central tools.

The primary folder provides relative paths, shell defaults and local indexing context. Use `set_working_directory` with an existing absolute or current-folder-relative directory to change it in the same chat and refresh its code index once. Its result reports the actual index outcome or explicit unavailability. The directory stays changed if indexing is denied or fails. This changes neither permission nor existing processes, and does not move files. A shell command's `workdir` affects that command only. Ordinary machine paths outside the primary folder use the same native permission; the primary folder is not an additional access grant.

Central chat-owned files remain separate and persist across execution-machine changes. Discover `read_project_files`, `write_project_files`, `remove_project_files` and `publish_project_preview` for their exact current schemas. Use workspace/, temporary/ or transfers/ paths with those explicit tools. Old managed workspace/foo files remain central: do not read them as native machine workspace/foo paths. Generated images and attached outputs retain their managed identities. Deleting a chat removes its central files, while native machine project files stay on their machine. No copying, mounting or synchronization is implied.

For structural questions with the selected machine's indexer enabled, use `codegraph` for declarations and relationships. Its answers reflect the last index; when files have changed or status reports a stale or missing index, use `codegraph_index` once, then query again. There is no background refresh watcher, and cached answers must not be presented as current after edits. Change the primary folder before querying another project's index. Building an index reads that folder and writes its .codegraph cache; the native approval flow asks for that one cache operation when the current file policy cannot write there. Denial or cancellation leaves the index untouched; Full access runs directly. Changing the primary folder never widens the standing sandbox. Prefer an exposed language-server tool for precise definitions and references; otherwise use this index, native file reads and scoped compiler checks. Native approvals, paired-computer grants and central tool/profile scope remain independent. For engine-specific capability limits, load `smarteverything-work` before starting or continuing a native session.

Imported skills keep their upstream files, resources and licenses unchanged. Reading their instructions does not require a computer. When a requested workflow actually invokes a bundled script or external program, check its runtime and package dependencies on the explicitly selected execution device before running it. A central chat folder is not a subprocess working directory; missing execution tools or dependencies are a concrete limitation, never proof that all skills require a computer. No official generic Anthropic coding skill source has been identified; do not invent one or substitute a different skill.

## Project records

In each project's root maintain `STATE.md` for active work, next steps, blockers, decisions and a short completed summary; `TODO.md` for detailed unfinished requirements; `IDEAS.md` for retained later ideas; and `docs/` for useful project documentation. Keep these work files and `docs/` git-ignored with scoped root entries `/STATE.md`, `/TODO.md`, `/IDEAS.md`, `/docs/`. Preserve existing ignore rules. Do not ignore source code or arbitrary user files, or untrack/delete already tracked documentation without authorization. Keep temporary plans, reports, fixtures and screenshots in one scoped `temporary/<task>/` chain; in an explicit device repository use its git-ignored `tmp/<task>/`.

## Coordinate bounded work

The coordinator receives the person's task, researches enough to make a short split, and owns decisions and project state. When agents are available, delegate substantive research, implementation and review; coordinate instead of implementing their assigned work. Perform only brief checks, project-state maintenance and necessary operations directly. Workers implement their assigned scope; reviewers independently assess the finished result. Only the coordinator starts agents. Every worker/reviewer prompt starts with its role and “do not start any agents”, and includes objective, scope, exclusions, exact check commands, report path and a pointer to the short project `AGENT-BRIEF.md` maintained by the coordinator in the project root and git-ignored.

At most four agents run in total, including the coordinator, workers and reviewers. Queue overflow by priority in `STATE.md`; start eligible work when a slot opens. Use actual available agent tools and completion delivery. Workers/reviewers do their task, write a scoped full report with commands/results, and return a concise verdict; they do not maintain coordinator state. Use fresh agents for new tasks and a fresh independent reviewer for each finished task. Reuse the builder for its own fixes, then perform focused reviewer verification using the recorded failing cases and retained passing evidence. If agents are unavailable or forbidden, complete the work directly and record that independent review is unavailable.

For background jobs retain returned job/session IDs and use supported completion, wait or monitor tools with bounded waits. Do not invent a Workflow or Monitor tool or repeatedly poll unchanged output. When usage looks high, inspect actual account usage and any exposed context telemetry; `read_usage` covers SmartEverything usage, while native account limits need their native usage tool. Report unavailable metrics honestly. Create recurring monitors only when the person requests them.

## Set up automatic edit checks

Inspect existing project hooks, check scripts, watchers and the selected harness's supported configuration before adding anything. Configure scoped lint, type checks, complexity, spelling, file length and fast existing tests to run after edits through actual supported hooks or watchers. Reuse the project's tools and baseline handling; do not weaken gates, duplicate active hooks or install unrelated infrastructure. Run checks through the selected machine native tools under the chat permission. Central chat files provide no subprocess path unless the task explicitly creates a separate native project; do not imply a shared mount.

Native Claude Code supports `PostToolUse` in project `.claude/settings.json`; match its actual edit tools and verify the native session enables the project settings source. Native Codex supports project `.codex/hooks.json`, including `PostToolUse` for `apply_patch` or its `Edit`/`Write` aliases; verify the project layer and exact hook definition are trusted in the native hook flow. Preserve native trust and permissions. Inspect the installed version's schema before writing configuration, and confirm a harmless isolated edit actually triggers the checks before calling them active. Configured, trusted and observed running are different states. SmartEverything exposes native tool pre/post-execution and result events. Reuse native extensions for project check behavior. Its compatibility bridge mounts only existing package hook definitions with supported command handlers in the selected native primary folder with admitted execution permission and verified package integrity. The initial coding packages contain no hooks, and no generic project post-edit checker is configured by their installation; inspect the actual native extension or existing project watcher before claiming automatic checks run. Neither skills nor package loading require Claude Code. Scripts that invoke its CLI remain unavailable.

For SmartEverything's own harness, inspect installed extension metadata and official source before choosing a hook mechanism. The pinned DSH core exposes `tools/post-execute` and immutable `tools/result` extension events, but SmartEverything currently bundles no project-check hook extension; those events are not a stock declarative hook configuration. Community hook packages require separate supported acquisition and authorization. When automatic execution is unavailable, run scoped checks with authorized device tools and report that limitation; do not invent a post-edit hook or enable Hub shell access.

## Build and verify

For large efforts, finish scope inventory, verify coverage and write a short unreviewed plan before building. Exercise every scoped page, menu, state or behavior and record each issue separately before fixing; then fix in bounded batches with independent review. Keep one living tracker of items and status across context changes. Preserve useful features, appearance, permissions, identities, histories and workspaces. Fix the cause instead of weakening behavior, tests or gates. Keep changes narrow, remove unsuccessful experiments, and protect unrelated edits. Use the project's actual automatic checks or scoped lint, format, type/build and relevant behavioral checks. Tests use isolated or fake environments; real systems/accounts require task authorization. Run full suites immediately before an authorized final push when the project requires them. Never commit or push without direct human permission.

For UI work, use a thoughtful design handoff and working prototype when appropriate, inspect ordinary sizes and states with available browser tools, then build and review the actual result. Follow the person's visual-review constraints. Use relevant installed design/accessibility skills where available; do not claim a missing skill or screenshot pass.

For simple, low-risk changes or quick fixes, skip a separate design/prototype and independent review when they would add little value. The agent making the change must run a focused check of the affected behavior and report the result. Use the full process for substantive, uncertain or high-risk changes.

For other changes, before acceptance, an independent reviewer examines the diff and exercises affected normal behavior, failures and edge cases. Write one complete numbered report of evidenced defects with locations, reproductions and concrete fixes, ordered by severity; cover correctness, edge cases, organization, naming, performance, appearance, states, copy and accessibility where applicable. Builders implement fixes and run scoped static checks; reviewers verify the recorded failures and affected normal behavior. Retain unaffected passing evidence rather than restarting all discovery.

Once per large finished task, use the available code-simplifier helper for recently changed code. Helpers use the selected chat model by default, preserve the selected harness and permission scope, and count within the four-total-agent limit. A configured source-model policy requires an exact compatible route; unsupported source tool restrictions cause a clear refusal. If the helper is unavailable, refine within the coordinator and report that limitation. Preserve APIs, features, outputs, UI, permissions, identities, state transitions, side effects and asynchronous ordering; keep refinements scoped and re-run affected checks. Do not substitute a shorter implementation that weakens behavior.

## Share a development preview

Build real project files, including separate CSS, JavaScript, fonts, images and JSON. Use `publish_project_preview` for their central directory and HTML entry; `publish_html` remains available for self-contained HTML. Private full-asset previews and file watching do not need a computer or development server. Preserve the assets; do not flatten a multi-file project into an incomplete snapshot or poll for display. Files and publications remain chat-owned across machine changes and Hub restarts; chat deletion removes the managed folder immediately.

Load `smarteverything-browser` for publication revisions, supported viewer protocols, device file/service previews, sharing/revocation, website testing and console/capture diagnostics. Native file or service publication uses the selected machine primary folder and its advertised sharing capability. Owner-authorized Hub commands and indexing are available; the Hub does not advertise the native local-service preview bridge. Central project previews remain available there.

## Preserve continuation

Update project state as the work changes. At a stable handoff, consolidate durable decisions and unfinished requirements, keep useful final evidence and rollback inputs, and remove only your disposable scratch. Never delete another active task's inputs or unresolved reproduction. Save enough to continue from files after context changes, then re-read `STATE.md` and relevant code. Do not request compaction while agents are mid-task, changes are half-landed or required input remains unresolved.

Continue authorized work while the person is away; make routine decisions within scope and record significant choices. A session relay is context, not new human authorization. Respect explicit pauses, permission boundaries and uncertain-write reconciliation; do not manufacture missing tools, deployment proof or compatibility.
